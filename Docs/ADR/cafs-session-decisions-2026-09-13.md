# CAFS Session Decisions — 2026-09-13

Consolidation pass. Everything below was decided or resolved in this session's conversation. Not yet patched into fs.info/config.fs/adr-log.json — this is a working reference, not a replacement for that.

## On-disk format fixes
- **B-tree branching factor**: 254 slots, not 255. The documented 255-slot layout (8B header + 255×16B slots = offset 8–4087) overlaps the checksum trailer's fixed last-16-bytes position (offset 4080–4095) by 8 bytes when a node is full. Fix mirrors ext4's dx_tail precedent: cap at 254 slots (4064B, offset 8–4071), 8B pad, trailer at 4080.
- **`namespace_structure_id`**: already committed, fs.info v21 Superblock offset 84–87 (ADR-034). Confirmed done, not open.
- **ADR-013 permission-duplication corollary**: closeable. Identifier Table (7a) carries `unix_mode+uid+gid` in the critical tier, satisfies the corollary now that an inode-equivalent actually exists.
- **`raw` full-allocation, zero vs. uninitialized**: resolved toward ext4-style unwritten-extent semantics — mark the extent allocated-but-logically-zero, return zero on read of a never-written range, physically write only when real data lands. Avoids both the stale-data leak and the double-write amplification of upfront zero-fill. **Needs a format change**: one bit in the 16-byte extent entry (`start_lba`+`length`) for the "unwritten" flag — not yet spent. **Verified tonight** (was asserted from general knowledge earlier, not checked): the core mechanism is confirmed directly from a 2007 ext4 kernel mailing-list exchange — "the extent doesn't have to be explicitly zero filled on the disk, by virtue of the fact that the uninitialized flag will cause reads to return zero." Concept holds. Honest caveat worth carrying forward: this exact area has a real history of subtle corruption bugs in ext4 even after ~18 years of hardening — partial-zeroing edge cases, interaction with delayed allocation, stale data exposure on power loss during conversion. Worth being deliberately careful in CAFS's implementation, not treating the flag bit as a trivial addition once designed.
- **`raw`-in-snapshot**: not a policy anymore — raw files are categorically excluded from snapshot scope (no CoW, nothing for a snapshot to reference). `[snapshot].raw_file_policy`'s skip/warn/block field is moot; can be removed, or kept only as an optional notification toggle (not a behavior fork).

## WAL
- **Physical model**: `raw`-tagged blocks, allocated at mount time in 512MB chunks, handed over by the allocator (mechanism/"permission slip" details deferred to the allocator discussion). If a full 512MB contiguous run isn't available, chain multiple variable-length contiguous runs instead of forcing one exact size.
- **Rotation model**: not a ring buffer, not an array. Older entries are at the **head**; head entries get applied and the head advances/shrinks by `block_size` increments as each block's worth is confirmed applied. When the current chunk fills, allocate a new chunk for further writes while the old one keeps shrinking/draining; once fully drained, it's destroyed. "Another idea" for finer-than-block_size granularity mentioned but explicitly deferred by you.
- **Overflow behavior**: default is to stall when no 512MB chunk is available; under high I/O, fall back to `block_size`-granularity allocation instead of stalling, to keep writes flowing.
- **`wal_lba` (Function Table)**: a fast-path pointer only, not authoritative — Zone Table is ground truth. Holds (or needs to hold) the current active WAL chunk location(s) so fsck/recovery can jump straight there instead of rediscovering them by scan. Needs to represent a **list** of chunk locations (current + still-draining), not a single 8-byte pointer — proposed reusing the 16-byte extent-entry shape for this.
- **Refcount/collision safety**: resolved implicitly — since WAL blocks are ordinary `raw`-tagged allocations, they go through whatever collision-protection mechanism already covers raw files. No special-cased mechanism needed; this closes the refcount-integration gap flagged earlier in the session.
- **Recovery ordering**: after confirming mount works, fsck/recovery fixes WAL first, before anything else. (Note: this ordinary-mount-time sequence isn't written into fs.info's Section 14, which currently only covers anchor-region corruption tracks — a documentation gap, not a design gap.)

## Identifier lifecycle
- **Resolved as "both"**: refcount-zero → immediate retirement (cheap, inline) + entry copied into the Recently-Zeroed Queue (8b) using its existing `tag` field, extended with a new tag value for "retired identifier, slot available for reuse." Actual reclaim/reuse work is offloaded to defrag/balance/storage-expander reading that queue asynchronously — same pattern already used for data-block reclaim, not new plumbing.
- Snapshot-safety already covered: `identifier_refcount` accounts for snapshot-root reachability too, so a reused identifier can't collide with one still referenced by a retained snapshot.

## Handlers / process architecture
- **Confirmed processes**: `master` (top-level supervisor), `mntproc` (FUSE handler, **Rust**, not C — correction from earlier ADR wording), `defrag.rs`, `balance.rs`, `scrub.rs`, `store_mgr.rs` (= storage expander, described as "the fast scrubber"), `smart_handler.py` (3 modes), Hash Daemon (Python, socket-based), `tasker.rs` (contains both FS Tasker and Routine Tasker logic).
- **FS Tasker**: runs the non-blocking, on-demand filesystem scripts during I/O (e.g., `--type=trends`, hash queries) — a code role, not necessarily a separate OS process.
- **Routine Tasker**: scheduler function — checks I/O stats + config, decides whether to run a routine now, and computes a next-check schedule.
- **Routine Tasker priorities — three, not four**:
  - **Normal**: idle/low-I/O, on configured interval. Runs storage expander → balance #1 → defrag → balance #2 → SMART, in that order (storage-expander clears ghost/deleted-but-uncommitted entries first, balance closes empty gaps, defrag merges partial blocks which creates a new gap, balance closes that too).
  - **Urgent** (renamed from "PanPan"): two variations. **A** = accumulated maintenance debt (30+ days since last Normal run) — runs the full Normal set at a little higher priority. **B** = free space critically low (<15%) — narrower, faster set (storage-expander + high-speed balance, skip defrag) since the priority is space back *now*, not thoroughness.
  - **Check**: full A-to-Z drive scan, daily/weekly/monthly/6-months/1–2 years cadence — this **is** what "scrub" means. Storage-expander is a distinct handler, not a subset of Check/scrub — "scrub" was initially mixed up with "remove excess," corrected: scrub means integrity verification (read + checksum + repair from redundancy), not reclaim.
- **Defrag/Balance scheduling by media type**: on-demand-only (user-triggered config action) for SSD; automatic + config-driven for HDD, matching the write-endurance/no-seek-benefit finding for SSD.
- **Crash isolation for nested supervision**: Linux `PR_SET_CHILD_SUBREAPER` (via `prctl`, usable from Rust through the `nix` crate) — if master marks itself a subreaper, any of tasker's still-running children get reparented straight to master if tasker dies, no advance notice needed. Windows equivalent: Job Objects (assign the whole tree, monitor regardless of who spawned whom).
- **New tasker shape (direction, not finalized)**: master dispatches tasker on a set interval; if tasker decides something needs to run, it notifies master of its intent before acting; tasker and the Allocator then communicate directly. Explicitly deferred by you until after the allocator's home is settled — noted as complementary to (not a replacement for) the subreaper mechanism, since subreaper gives automatic *detection* of an orphan and the intent-notification gives master the *context* needed for meaningful damage recovery.

## Concurrency
- **Model**: per-zone/block/B-tree-leaf `RwLock` — many concurrent readers, or one exclusive writer, never both, matching Rust's `RwLock<T>` (the compile-time borrow checker is the intuition, `RwLock` is the actual runtime mechanism across threads). Two unrelated areas (e.g. `/home` and `/logs`) can write concurrently with no serialization between them.
- **Fixed at mount** — the one knob explicitly excluded from live reconfiguration, for the specific reason that live-switching it was the root cause of a real data-race found in an earlier design (Gemini-audited).
- **Multi-zone operations (e.g. cross-directory rename)**: resolved via a fixed global lock-acquisition order (e.g., always the numerically lower zone ID first), holding both locks for the whole operation. This is both deadlock-free and preserves POSIX rename atomicity — rejected the alternative (release-then-reacquire sequentially) because it opens a visibility gap where the file resolves from neither the old nor new path.
- Same-directory rename only ever touches one zone — trivial, no ordering issue.

## Permissions
- **Linux**: `default_permissions` FUSE mount option — kernel's own `generic_permission()` enforces, mntproc just needs to report accurate `st_mode`/`uid`/`gid` via `getattr`. No hand-rolled permission logic needed.
- **Windows/WinFsp**: same shape — WinFsp passes the file's security descriptor to Windows' `AccessCheck` API, kernel's Security Reference Monitor does the actual enforcement. WinFsp auto-translates POSIX uid/gid/mode into a compatible security descriptor (SFU/Cygwin-style mapping). For full native ACL control, WinFsp also has a `FileSecurity` option (SDDL-based) as a richer alternative.
- **Implication**: IO Engine and Allocator can skip permission sanity-checks entirely — that's the kernel's job on both platforms now. **Does not extend** to filesystem-*state* rejections (no free space, emergency_mode active, raw/snapshot conflicts) — those are a different category the allocator still owns.

## Allocator architecture
- **Daemon vs. library**: not a single global choice — both are supported, gated by preset. Safety preset biases toward separate-process (plus more checking); performance/balanced default to library (in-process). This is more implementation surface than picking one, accepted as the cost of the "max config" direction.
- **Code structure**: core allocation logic as one plain struct/module with an `allocate(request) -> response` / `free(request) -> response` shape, agnostic of caller. A shared trait (interface) defines that contract; two thin implementations satisfy it — one calling the core struct directly in-process (library mode), one serializing over a socket (daemon mode). Calling code in mntproc just holds "something implementing the trait," doesn't branch on which mode is active.
- **Concurrency research finding (ntfs-3g, verified from actual source)**: ntfs-3g calls `fuse_loop()`, never `fuse_loop_mt()` — it avoids concurrency entirely by never running FUSE multithreaded, confirmed deliberate via a first-party code comment about directory-access races "when fuse is multithreaded." Real, mature precedent for "serialize everything" as a legitimate safety-preset option, at real throughput cost.
- **A0–A4 are presets, not algorithms** — confirmed terminology fix, keeping the legacy A0–A4 names anyway.
- **Presets as config bundles**: Performance/Balanced/Safety/Custom are named starting bundles of knob values in the allocator's config section, not a separate axis from hardware/health-detected starting point. Safety biases toward safer execution (separate process, more checking) but still allows high performance if the drive is healthy — a bias, not a hard cap.
- **The seven knobs (complete, corrected list)** — Concurrency (fixed, not hot-swappable) + six hot-swappable: **Placement** (Sequential-Append/Locality-First/Parallel-Spread — this *is* the free-space search strategy, not a separate 8th knob), **Preallocation** (Off/On(N)), **Delayed Allocation** (Off/On), **Read-Ahead** (128KB/256KB/4MB), **Flush Interval** (Short/Medium/Long), **Bad-Block Relocation** (Reactive/Proactive/Off — Proactive uses trends' pending-sector trajectory to relocate ahead of failure). Values and reasoning given for all seven; numeric thresholds (15% free, S≤0.3, exact flush-interval durations) are still placeholder estimates, never measured.
- **What actually makes a knob safe to hot-swap**: not "standardized values" — it's whether the knob requires synchronizing against operations already in flight. The six non-concurrency knobs don't (changing read-ahead only affects the next read, etc.); concurrency does, which is why it's the one exception. A future knob would need the same no-in-flight-sync property to qualify, not just a tidy value set.
- **A4/Emergency's original bug is fixed by the hot-remount idea**: the original static model had no hysteresis (permanently trapped in Emergency once triggered). Routing hard-floor events through a real remount rather than a live in-place switch both avoids the concurrency-overlap hazard and gives a natural exit once a later remount's fresh detection shows improved health.

## SMART
- **Three invocation modes**: `--type=smart` (raw attribute values, user-configurable cadence), `--type=avg` (feeds the other two, fixed cadence, exact computation/window still unspecified), `--type=trends` (smart's values + trend buckets, fixed cadence).
- **Precedence**: smart's acute signal wins over trends on disagreement by default, user-configurable — **except** a hard floor that can never be disregarded regardless of config.
- **Hard floor, ATA**: SMART 187 (Reported Uncorrectable Errors) and 198 (Offline Uncorrectable Sector Count) — both literally "uncorrectable," matches the non-negotiable framing directly. 197 (Pending), 5 (Reallocated), 188 (Command Timeout) are precursor/gradual signals, feed the caution/trend score instead, not the hard floor. Explicitly *not* using the drive's own aggregate `smartctl -H` PASSED/FAILED verdict as an override trigger — known to be unreliable in both directions.
- **Hard floor, NVMe**: `critical_warning` bits 2 (NVM subsystem reliability degraded) and 3 (media placed read-only). Bit 2 has real precedent — VMware vSAN treats it as its automatic-action trigger while deliberately not auto-acting on things like volatile-memory-backup failure (bit 4) for being too vendor-specific/noisy. Bits 0 (spare capacity) and 1 (temperature) are gradient/wear indicators, not override triggers.
- **On-disk SMART table**: the five Backblaze-validated, cross-manufacturer-consistent ATA attributes — 5, 187, 188, 197, 198 — stored as raw values with timestamps (need history for trend computation, not just a snapshot).
- **Trends output shape**: multiple named values, not one aggregate score, since different allocator knobs need different inputs — likely a per-attribute trajectory/concern value for each of the five, plus one aggregate composite shaped for the allocator's zone-weighting. Exact field list not yet pinned (this is the live open task).
- **Signals layer implemented in `smart_handler.py`, additive alongside the existing z-score mechanism**: `workload_bias`/`r_write` (fixed-cap normalization, recalibrated denominator/threshold), `health_composite`, `pending_trajectory`, `write_size_cv`, `free_space_percent` pass-through, `hard_floor_active` (monotonic global flag, single writer). `health_composite` and `pending_trajectory` both use EWMA (α=0.18 / α=0.3 respectively) over bucket history rather than raw values or a first-to-last delta — smooths isolated one-off errors while still responding to a genuine sustained trend, matching real disk-failure-prediction research's finding that recent *change* in a cumulative counter matters more than its raw accumulated value. `health_composite` now takes 5 inputs, not 3: the three ATA attributes (5/197/188) plus CAFS's own on-disk `checksum_mismatch`/`host_relocations` counters (sourced directly from `reconcile_smart_tables`'s already-real `primary` array, no placeholder needed for these two specifically) — complementary evidence, since these two catch silent corruption that never crosses whatever threshold makes drive firmware report an ATA error at all. Every history input gracefully degrades to a single-point EWMA (i.e., just that point) when full multi-hour history isn't supplied yet, so the code runs correctly today and improves automatically once real bucket-history plumbing exists — verified via three smoke tests (clean baseline, on-disk evidence correctly dominating the composite, and a synthetic climbing-pending-sector sequence producing a sensible trajectory value).
- **Hard-floor response protocol (your proposal, agreed)**: switch to the safest mode possible, which requires a hot remount for the concurrency knob specifically (unless config explicitly forbids it), determine which general area (zone-level, via Zone Table's existing health-aggregation role, ADR-035) the floor event affects, then warn or error to notify the user their hardware is failing/has failed. **Flagged risk, not yet resolved**: the hot remount must fully drain/quiesce in-flight I/O under the old concurrency regime before switching, or it reintroduces the exact overlapping-epoch race that got live-switching rejected in the first place.

## TRIM
- **Mechanism precedent (researched)**: batched/coalesced (Linux `FITRIM`/`fstrim`, ZFS `autotrim`/`zpool trim`) is the cross-ecosystem-consistent default; inline/continuous discard is the exception, since it fragments into many small commands competing with foreground I/O.
- **Per-zone "needs-trim" flag** — direct GFS2 precedent (flag per resource-group, reset on dealloc, set after successful trim), maps cleanly onto the existing Zone Table.
- **Hybrid model (your call, agreed)**: most reclaimed space waits for the batched sweep; WAL-chunk destruction, scratch-area frees, and low-free-space conditions get immediate/eager discard instead — this sidesteps the usual inline-discard downside since those are already naturally large, coarse ranges, not many small ones.
- **Rate limiting**: self-throttling in the trim-issuing code (token bucket, tracking your own issued bytes/sec) — not an OS or FUSE feature, same as how ZFS's own `-r` rate limit works. Measuring the *device's total* I/O (not just your own issuance) uses `/proc/diskstats` (Linux, per-partition sector counters, poll-and-diff) or `IOCTL_DISK_PERFORMANCE` (Windows — verified tonight directly against Microsoft's own driver docs: returns a `DISK_PERFORMANCE` struct with cumulative `BytesRead`/`BytesWritten`/`ReadCount`/`WriteCount`, same poll-and-diff shape).
- **Windows side — real, unresolved constraint**: `IOCTL_STORAGE_MANAGE_DATA_SET_ATTRIBUTES` with `Action=Trim` is explicitly documented as unsupported for user-mode applications. Windows' Optimize Drives / `fsutil disabledeletenotify` is gated to NTFS/ReFS only (confirmed via the exFAT/FAT32 precedent — neither gets automatic Windows TRIM either, despite being native Microsoft formats). WinBtrfs proves third-party TRIM is achievable on Windows, but specifically because it's a **kernel-mode** driver — doesn't transfer to a WinFsp (user-mode) architecture. No evidence found either way that WinFsp itself provides a relay path.
- **Your resolution**: a narrow, single-purpose kernel-mode driver that does nothing but relay trim requests — minimal attack/crash surface, `__try`/`__except` for fault handling (real Windows mechanism, though not universally fault-proof — a few fault classes are unconditionally fatal regardless). Documented tradeoff, not solved around: kernel drivers need EV code-signing + Microsoft Hardware Dev Center attestation to load without test-signing mode enabled — a process/cost hurdle independent of code correctness. **Confidence note**: this specific requirement is well-established, stable, common knowledge — high confidence — but wasn't specifically re-searched this session the way the other flagged items were, unlike everything else in this file. You've noted this goes in the README as a stated compromise.

## Allocator: modes, presets, and hot-swap (added this pass)
- **Modes vs. presets, two-stage**: 4 total modes — Performance, Safety, Balanced, Custom. Modes don't pick a preset directly; a mode filters which of the X (A0–A4-style) presets are even *eligible*. If exactly one survives the filter, it's auto-selected. If more than one survives, trends' values break the tie among the eligible set.
- **A0–A4 are legacy names for presets**, not algorithms (confirmed terminology, kept anyway).
- **Windows TRIM path decided**: a narrow, single-purpose kernel-mode driver whose only job is relaying trim requests — minimal surface, `__try`/`__except` fault handling. Documented tradeoff (driver signing hurdle) goes in the README as a stated compromise, not solved around.
- **Knobs are independent, confirmed**: each of the six hot-swappable knobs (Placement, Preallocation, Delayed Allocation, Read-Ahead, Flush Interval, Bad-Block Relocation) has its own lock/stabilization state and its own trigger condition. A knob changes the moment its own condition is met and it isn't currently locked — zero dependency on any other knob's state. Implies six separate generation-counters/`Arc` slots, not one bundled swap (this overturns the "trigger config change to A1" framing in the recovered DeepSeek draft — that document's bundled-swap assumption doesn't survive, its timing-tier *structure* does).
- **Recovered prior research (DeepSeek draft, premature but salvageable)**: three-tier timing model — a poll interval, a decision window requiring N consecutive agreeing readings before acting (anti-thrashing/hysteresis), and a stabilization lock after a change, broken immediately by a condition-variable emergency wake for hard-floor-class events (bypasses both the consensus requirement and the lock). The original draft assumed a 30s poll computed by an independent monitor thread — both superseded: poll cadence is actually trends' invocation cadence (see below), and the computation is smart_handler's job, not a separate monitor.
- **FS Tasker's SMART invocation cadences**: `--type=trends` every 15 seconds. `avg_maker` runs on a longer, separate cadence — at least 1 minute, capped below 50 minutes. `--type=smart` itself runs on a user-configurable cadence per existing config.
- **IPC design, handler ↔ allocator**: reuses existing mechanisms rather than adding a new channel. `smart_handler.py` → mntproc: unchanged, existing stdin/stdout pipe (ADR-001). mntproc → allocator: the same trait already designed for the daemon/library split (`allocate`/`free`) gets one more method, `update_knob(knob_id, value)` — library mode calls it directly in-process, daemon mode sends it as a new message type on the existing socket, not a new connection.
- **I/O Engine counters, non-blocking**: plain atomic increments (`AtomicU64::fetch_add`, relaxed ordering) for read count, write count, bytes read, bytes written, and write-size sum+count (sufficient for a mean, no full histogram needed unless trends wants more). Genuinely lock-free for values that don't need to be updated jointly with another value in the same instant.
- **Trends' output is two families of values, not one**: health-derived (the five ATA attributes' trajectories, already covered) and workload-derived (Workload Bias and friends, computed from actual I/O counters) — corrected from an earlier assumption that trends was primarily health-driven.
- **Workload Bias formula, structure confirmed but flagged broken (see Open Questions)**: `B = (mean_write_size_in_64KB_units) / (1 + R_write)`. R_write = normalized average LBA distance between consecutive writes (0 = sequential, growing with randomness), sits in the denominator specifically to (a) avoid divide-by-zero and (b) make the randomness penalty smooth rather than a binary cliff.
- **Research done tonight (allocator-relevant), corrected after re-verifying against primary source directly**: Linux's readahead logic (`mm/readahead.c`, fetched and read directly, not taken from a secondary source) is simpler than a continuous normalized-distance score, but not in the exact shape first reported here. Real mechanism: an index-adjacency check (`index - prev_index <= 1`) catches the trivial sequential case; if that fails, it falls back to inspecting actual page-cache history for a contiguous run (`page_cache_prev_miss`) rather than comparing offset distances; on failure it does a plain non-speculative read for exactly what was requested and leaves the readahead window state untouched (does *not* shrink to a small probe size — that detail was wrong). Directionally still a useful alternative paradigm to R_write's continuous-distance approach (cache-history-based, not distance-based), just don't carry forward the "prev_pos within one page" / "shrinks to 2-page probe" specifics, both incorrect.
- **`/proc/diskstats` independence claim, now actually verified** (`include/linux/part_stat.h`, fetched directly): not generic atomics — specifically per-CPU counters (`__this_cpu_add`, no cross-CPU sync on write) summed across all CPUs at read time with no lock coordinating the sum against concurrent writers. Confirms the "independent, non-jointly-consistent counters are standard practice" point, more specifically and more strongly than first stated — but this wasn't checked against source before it was first asserted a few turns back, only just now.
